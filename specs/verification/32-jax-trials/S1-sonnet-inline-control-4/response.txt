Your symptom — tiny timer reading, latency that grows with sequence length — is actually two separate phenomena that get conflated. Let's build a repro that cleanly separates them rather than guessing.

`★ Insight ─────────────────────────────────────`
JAX's `jit`-compiled functions return **immediately** with a `DeviceArray`/`jax.Array` future the moment the op is *dispatched* to the accelerator — not when it finishes. `time.perf_counter()` around a bare call measures "how long it took the Python/XLA runtime to enqueue the work," which is often microseconds, regardless of how much GPU/CPU time the kernel actually takes. This is by design (async dispatch lets Python race ahead and queue more work), but it makes naive timing lie to you.
`─────────────────────────────────────────────────`

The second candidate — latency scaling with input length — has two very different root causes that produce opposite remediation:

1. **Recompilation**: `jit` traces and compiles a new XLA program for every distinct `(shape, dtype, weak_type)` signature it sees. If your inference loop feeds variable-length sequences straight into a jitted function, every new length is a cache miss — full trace + XLA compile — which can take hundreds of ms to seconds, dwarfing actual execution.
2. **Genuine FLOP growth**: longer sequences really do require more compute (e.g., O(n²) attention), so some length-dependence is expected and correct.

The repro below distinguishes these by calling each length **twice** and comparing first-call vs. second-call latency.

**File: `jax_latency_repro.py`**

```python
"""Repro/diagnosis for JAX inference latency that looks tiny but isn't."""
import time
import jax
import jax.numpy as jnp
import numpy as np

# Print every compilation event to stderr as it happens — hard evidence,
# not inference, for whether a given call triggered a trace+compile.
jax.config.update("jax_log_compiles", True)


def toy_inference_step(params, x):
    """Stand-in for a real model step: one linear + attention-like block.

    x: (seq_len, d_model) — seq_len varies call to call in the demo below.
    """
    w1, w2 = params
    h = jnp.tanh(x @ w1)
    scores = h @ h.T  # O(seq_len^2) — deliberately length-sensitive
    attn = jax.nn.softmax(scores, axis=-1)
    out = attn @ h @ w2
    return out


jit_step = jax.jit(toy_inference_step)

d_model = 64
key = jax.random.PRNGKey(0)
w1 = jax.random.normal(key, (d_model, d_model))
w2 = jax.random.normal(key, (d_model, d_model))
params = (w1, w2)


def naive_time(fn, *args):
    t0 = time.perf_counter()
    out = fn(*args)
    t1 = time.perf_counter()
    return t1 - t0, out


def honest_time(fn, *args):
    t0 = time.perf_counter()
    out = fn(*args)
    jax.block_until_ready(out)  # works on pytrees, not just single arrays
    t1 = time.perf_counter()
    return t1 - t0, out


print("=== Phase A: naive timing (reproduces the 'suspiciously small' number) ===")
x = jax.random.normal(key, (128, d_model))
dt, _ = naive_time(jit_step, params, x)
print(f"naive (unblocked) call: {dt*1000:.4f} ms  <- this is dispatch time, not compute time")

print("\n=== Phase B: honest timing with block_until_ready ===")
dt_honest, _ = honest_time(jit_step, params, x)
print(f"blocked call:           {dt_honest*1000:.4f} ms")
print(f"ratio honest/naive:     {dt_honest/dt:.1f}x  <- the gap IS your 'end-to-end is much larger' symptom")

print("\n=== Phase C: sweep lengths, first-call vs steady-state (recompile vs real scaling) ===")
lengths = [17, 33, 64, 128]
for n in lengths:
    xn = jax.random.normal(key, (n, d_model))
    t_first, _ = honest_time(jit_step, params, xn)
    t_second, _ = honest_time(jit_step, params, xn)  # same shape -> cache hit
    print(f"len={n:4d}  first_call={t_first*1000:8.4f} ms  second_call={t_second*1000:8.4f} ms  "
          f"delta={  (t_first-t_second)*1000:8.4f} ms")
    # Large delta + a "Compiling ..." log line above => recompilation, not real work.
    # Small delta, smooth growth with n => genuine O(n^2) cost, not a bug.

print("\n=== Phase D: isolate compile cost explicitly via AOT lowering ===")
for n in [17, 33]:
    xn = jax.random.normal(key, (n, d_model))
    lowered = jax.jit(toy_inference_step).lower(params, xn)
    t0 = time.perf_counter()
    compiled = lowered.compile()
    t1 = time.perf_counter()
    out = compiled(params, xn)
    jax.block_until_ready(out)
    t2 = time.perf_counter()
    print(f"len={n:4d}  compile_time={(t1-t0)*1000:8.4f} ms  run_time={(t2-t1)*1000:8.4f} ms")
```

`★ Insight ─────────────────────────────────────`
`fn.lower(args).compile()` is the AOT (ahead-of-time) API — it splits "build the XLA executable" from "run it" into two separately-timeable steps, which is the cleanest way to prove recompilation is your bottleneck rather than inferring it from log noise. `jax_log_compiles` gives you corroborating evidence in the log stream, but the AOT split gives you a number you can assert on in a test.
`─────────────────────────────────────────────────`

Run this and look at the printed table from Phase C. The diagnosis follows directly:

- **If `first_call >> second_call` at every length, and you see `Compiling toy_inference_step...` log lines for each new length** → your bottleneck is recompilation from variable-length inputs. Fix: bucket/pad shapes (below).
- **If `first_call ≈ second_call` but both grow smoothly with `n`** → it's real work scaling, likely the O(n²) attention term; that's not a bug, it's physics, and you should optimize the algorithm (e.g. causal masking, flash-attention-style kernels) rather than the harness.

**Other places latency leaks past your timer** — even on top of async dispatch, any of these silently force a device→host sync and inflate "end-to-end" time without showing up around your `jit` call:

- `.item()`, `float()`, `int()`, or Python-level `if arr > 0:` on a device array
- `print(array)` or `np.asarray(array)` for logging
- `jax.device_put()` of a freshly-built NumPy array *inside* the loop (host-to-device copy every iteration)
- Re-defining the jitted function inside the loop, e.g. `jax.jit(lambda x: ...)` built fresh per call — this never hits the compilation cache because it's a new function object every time
- Passing a Python scalar (not a `jnp` array) whose *value* changes each call as a static/traced arg in a way that retraces (depends on how it's used in `jit`'s `static_argnums`)

### The fix: bucketing (if recompilation is the cause)

Instead of jitting on the raw variable length, round up to a small, fixed set of shapes so the compilation cache stays bounded:

```python
def run_bucketed(jit_fn, params, x, buckets):
    n = x.shape[0]
    bucket_len = pick_bucket(n, buckets)
    pad = bucket_len - n
    x_padded = jnp.pad(x, ((0, pad), (0, 0)))
    mask = jnp.arange(bucket_len) < n  # TODO: thread this into the model's softmax/pooling
    out = jit_fn(params, x_padded)
    return out[:n]  # slice back to the real length for the caller
```

`★ Insight ─────────────────────────────────────`
Padding changes the *math*, not just the shape: `jnp.pad` with zeros adds rows that the attention `softmax` in `toy_inference_step` will still attend to, silently corrupting every output row. A correct bucketing fix must mask the padded positions (e.g. `scores = jnp.where(mask[None, :], scores, -jnp.inf)` before the softmax) — otherwise you've "fixed" the latency and broken correctness at the same time.

def pick_bucket(length: int, buckets: list[int]) -> int:
    """Return the smallest bucket size >= length.

    buckets must be sorted ascending and cover your expected max length.
    TODO(you): choose the bucket boundaries/strategy. Tradeoffs:
      - Few, widely-spaced buckets (e.g. powers of two: 32, 64, 128, 256)
        -> fewer compiled variants (fast steady-state, small cache) but more
           wasted padding compute for lengths just over a bucket boundary.
      - Many, tightly-spaced buckets (e.g. every 8: 32, 40, 48, ...)
        -> less wasted compute per call but more distinct compiles (more
           cold-start latency the first time each bucket is hit, more
           cache memory).
    """
    for b in buckets:
        if length <= b:
            return b
    raise ValueError(f"length {length} exceeds largest bucket {buckets[-1]}")
